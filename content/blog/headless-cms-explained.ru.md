Без головы CMS отделяет управление контентом от презентации контента. Редакторы управляют контентом в одной системе, а разработчики предоставляют этот контент веб-сайту, приложению или другому интерфейсу через API или процесс сборки. 2.6 Под "бесголовной" частью подразумевается CMS не управляет окончательным рендеринговым слоем.

## Как работает безголовной CMS

Традиционная CMS часто сочетает в одном приложении хранение, редактирование, шаблоны и рендеринг страниц. Бесголовной CMS фокусируется на хранении и доставке контента.

1. Редакторы создают контент: CMS предоставляет админ-интерфейс и модель контента.
2. Содержимое хранится в централизованном порядке: CMS хранит структурированное содержимое в базе данных или хранилище.
3. Frontends fetch content: Веб-сайт, мобильное приложение или другой клиент получает контент через API или во время сборки.
4. Презентация отдельна: Интерфейс решает, как рендерить содержание.

| Модель                 | Хранилище содержимого | Доставка                           | Типичное помещение                                             |
| :--------------------- | :-------------------- | :--------------------------------- | :------------------------------------------------------------- |
| Традиционная CMS       | База данных           | Rendered by CMS runtime            | Простые сайты, управляемые в одной системе                     |
| Без заголовков API CMS | База данных           | REST/GraphQL API                   | Многоканальный контент, приложения, сложные модели             |
| Git основанный на CMS  | Файлы в Git           | Создать выходные/статические файлы | Статические сайты, документация, редакционные рабочие процессы |

## Преимущества и компромиссы

Платформы без Headless CMS полезны, когда один и тот же контент должен достичь нескольких фронтэндов или когда фронтенд команды хотят полностью контролировать рендеринг. Они также могут ввести операционную сложность: вы управляете контент-сервисом, схемой API, интерфейсной интеграцией и трубопроводом установки.

К числу распространенных компромиссов относятся:

- Гибкость и сложность: Вы приобретаете свободу фронтенда, но вы строите больше стека доставки.
- Структурированный контент и поток письма: Структурированные модели мощны, но они могут чувствовать себя жесткими для длительной формы.
- Зависимость от поставщика/API: Разрешенные платформы могут создать миграцию в том случае, если ваша модель содержимого или API является собственной.

## Где подходят инструменты на основе Git

CMS на основе Git может поддерживать бесконечную доставку, когда содержимое хранится как файлы и потребляется статическим генератором сайта или процессом сборки. Ключевое различие заключается в хранении: содержимое живет в Git хранилище вместо управляемого API базы данных.

Эта модель хорошо работает для блогов, документации и маркетинговых сайтов, где переносимость контента и Git история имеет значение. Для многоканальных приложений со сложными связями и поставкой в режиме реального времени может быть лучше подходит первый безголовной CMS API.
