A Git based CMS can handle drafts, revisions, and rollbacks by storing content as files in a repository and using Git history as the audit trail. Практическая ценность проста: вы можете сохранить работу, не опубликовав ее, проверить, что изменилось, и вернуть плохое редактирование без восстановления всей базы данных.

## Черновики как состояние файла

Во многих статических рабочих потоках сайта проект представлен передними вопросами, такими, как "проект: true". Файл может существовать в хранилище, в то время как генератор статического сайта пропускает его во время производственной сборки.

```yaml
---
title: "Draft post"
date: 2026-10-16T09:40:00Z
draft: true
---
```

Этот подход поддерживает состояние черновика ближе к содержимому. Объявление видимо: любой человек, имеющий доступ к хранилищу, может видеть черновик, даже если публичный сайт не отображает его.

## Изменения через коммиты

Каждое сохраненное или опубликованное изменение может создать коммит Git. Это дает вам читаемую историю для Markdown файлов, включая различия, метаданные автора и временные метки.

| Нужно                   | Git based workflow                               | Сделка                                                   |
| :---------------------- | :----------------------------------------------- | :------------------------------------------------------- |
| Посмотреть изменения    | `git diff` или diff запроса                      | Требуется очистить сообщения о коммитах                  |
| История аудита          | Фиксация журнала и винить                        | Модель доступа к репозиторию, которая может проверить ее |
| Восстановить содержимое | Вернуть фиксацию или восстановление версии файла | Восстановление может потребовать разрешения конфликтов   |
| Обзор перед публикацией | Ветка и запрос на слияние                        | Добавляет накладные для небольших правок                 |

Для команд, Pull Request'ов предоставляют редакционный порог. Для сольных авторов прямые коммиты в основную ветвь могут быть быстрее, но они удаляют шаг обзора.

## Откат как обычная операция Git

Когда сообщение имеет ошибку, Git позволяет вернуть коммит или восстановить предыдущую версию файла. После того как исправлена ошибка, ваш CI/CD трубопровод перекомпилирует и развертывает сайт.

Откачка файлового уровня узче, чем восстановление базы данных. Он может отменить одно сообщение, оставив другие изменения нетронутыми.

## Выбор рабочего процесса

Использовать прямые коммиты, когда показатели скорости и риск ошибки низкий. Использовать ветки и запросы на получение контента, когда требуется проверка, юридическое подтверждение или скоординированное время отпуска. Лучший рабочий процесс - это самый легкий процесс, который все еще дает вашей команде контроль контроля и рекуперации его потребностей.
