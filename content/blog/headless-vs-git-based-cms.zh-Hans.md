无头CMS和基于 Git 的CMS描述内容结构的不同部分。无头CMS将内容管理与演示文稿分开，通常通过API传送内容。基于 Git 的 CMS 将内容存储在 Git 仓库中，通常通过构建管道发布。

## 结构比较

| 区域         | 无头CMS       | 基于 Git 的 CMS    |
| :--------- | :---------- | :-------------- |
| 主要问题       | 内容是如何交付的？   | 内容存储在哪里？        |
| 存储         | 数据库或管理的内容存储 | Git 仓库中的文件      |
| 发货         | API请求/构建时间  | 静态构建输出通常来自CI/CD |
| 更改延迟       | 常常在发布后马上发布  | 在构建和部署后         |
| Versioning | 平台修订/工作流    | 本机Git历史记录       |
| 最合适的       | 多频道应用，结构化内容 | 博客、文档、营销网站      |

## 无头CMS适合时

无头CMS很适合于相同的内容必须输入多个前端，例如网站、移动应用程序和内部工具。当内容与复杂的关系、需要实时更新或需要颗粒化编辑权限时，也是适合的。

折衷是业务间接费用。您管理一个内容服务、API访问、方案更改和前端集成。

## 基于 Git 的 CMS 适合时

基于 Git 的 CMS 适合于内容主要面向文件，而主要发送目标是一个网站。 Markdown 文件在 Git 是可操作、可审核和易于版本。出版模式与静态站点发电机和CDN主机运行良好。

折衷是建立延迟和有限的运行时查询。如果您需要每个请求的个性化或复杂的关系查询，基于Git的静态工作流可能是限制性的。

## 混合方式

一些团队同时使用两种方法：一种基于 Git 的文件或营销内容的 CMS，另一种是应用程序数据的 API驱动的无头CMS。有用的决定并不是哪一类一般来说更好，而是每一种内容类型应在哪里存活以及应如何交付。
