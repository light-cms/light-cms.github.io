Редактор LightCMS предоставляет писателям визуальный редактор, сохраняя содержимое как Markdown и передний элемент в Git репозитории. Основная цель - уменьшить ошибки форматирования без извлечения содержимого из рабочего процесса на основе файлов.

## Что работает редактор

| Задача редактора                 | Что проверить                                     | Почему важно                                                               |
| :------------------------------- | :------------------------------------------------ | :------------------------------------------------------------------------- |
| Широкое текстовое форматирование | Заголовки, списки, ссылки, кавычки, блоки кода    | Авторам не нужно отлаживать синтаксис Markdown                             |
| Передняя субстанция              | Заголовок, дата, теги, описание, черновик статуса | Недопустимые метаданные могут нарушить статические сборки сайта            |
| Медиа                            | Изображение загружено, пути, alt текст            | Обработка активов часто вызывает некорректные ссылки на статических сайтах |
| Структурное содержимое           | Таблицы, списки задач, встраивание, математика    | Поддержка различных функций зависит от редактора и SSG                     |
| Markdown output                  | Чистый, рассеянный Markdown в Git                 | Качество выходной продукции влияет на длительную переносимость             |

Хороший WYSIWYG Markdown редактор должен сделать общие задачи написания легче, сохраняя предсказуемый вывод файлов. Если редактор создает шумный Markdown или неожиданно переписывает переднюю материю, то это создает трение для разработчиков, которые рассматривают различно.

## Передняя матрица и безопасность сборки

Ошибки фронт-матрицы являются распространенным источником неудачных статических сбоев при сборке сайта. Формовый редактор переднего дела может уменьшить ошибки, такие как некорректные даты, отсутствующие обязательные поля или неправильно сформированные YAML.

Сделка - гибкость. Строгая форма предотвращает ошибки, но они также могут блокировать настраиваемые поля, если редактор не разрешает схему или поддержку пользовательского ключа.

## Визуальное редактирование компромиссов

Визуальные редакторы полезны писателям, которые не хотят управлять сырым синтаксисом Markdown. Они менее полезны, когда команде требуется точный контроль над пользовательскими короткими кодами, необычными расширениями Markdown или специфичными для фреймворка компонентами. В этих случаях редактор должен сохранять необработанные блоки, а не переписывать их.

Мое мнение заключается в том, что визуальный редактор является ценным для Git издания, когда он сохраняет Markdown чистым и предсказуемым. Если он слишком много скрывается или генерирует проприетарный выход, он прежде всего подрывает преимущества переносимости при использовании Git.
