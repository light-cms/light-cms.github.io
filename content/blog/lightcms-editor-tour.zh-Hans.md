LightCMS编辑器在将内容保存为 Markdown 和 Git 仓库前缀时为作者提供了一个视觉编辑界面。主要目标是减少格式错误，而不要将内容从基于文件的工作流程中删除。

## 编辑器处理什么

| 编辑器任务           | 要检查的内容                | 为什么重要？              |
| :-------------- | :-------------------- | :------------------ |
| 富文本格式           | 标题、列表、链接、引用、代码块       | 作者不需要调试 Markdown 语法 |
| 前台事项            | 标题、日期、标签、描述、草稿状态      | 无效的元数据可以破坏静态站点构建。   |
| 媒体              | 图片上传，路径，alt 文本        | 资产处理常常导致静态站点链接中断。   |
| 结构化内容           | 表格、任务列表、嵌入、数学模式       | 功能支持因编辑器和 SSG 而变化   |
| Markdown output | Git 中的干净、可传播的Markdown | 输出质量影响长期可移植性        |

一个好的 WYSIWYG Markdown 编辑器应该使常见的写作任务更加容易，同时保存可预测的文件输出。如果编辑器出乎意料地产生噪音Markdown或重写前缀，它会给开发者审查差异制造摩擦。

## 前面事物和构建安全

前事项错误是静态站点构建失败的常见来源。基于表单的前缀编辑器可以减少错误，例如无效日期、 缺失的必填字段或 YAML 格式不正确。

权衡是灵活的。严格的表格防止错误，但也可以屏蔽自定义字段，除非编辑器允许架构或自定义密钥支持。

## 视觉编辑权衡值

视觉编辑器对不想管理原生Markdown 语法的作者很有帮助。当团队需要对自定义的短码、不寻常的Markdown 扩展或框架特定组件进行精确控制时，它们的用处就更小。在这种情况下，编辑应保留原始块，而不是重写原始块。

我的判断是，视觉编辑器对基于 Git 的发布很有价值，因为它能使Markdown clear和可预测。如果它隐藏过多或生成产权产出，它首先会损害使用Git的可移植性。
