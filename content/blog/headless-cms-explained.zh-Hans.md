无头CMS将内容管理与内容表达式分开。编辑器管理一个系统中的内容，开发者通过API或构建过程将内容传送到网站、应用或其他前端。“无头”部分是指CMS不控制最终渲染层。

## 无头CMS如何工作

传统的 CMS 常常将内容存储、编辑、模板和页面渲染合并在一个应用程序中。无头CMS的重点是内容存储和交付。

1. 编辑器创建内容：CMS提供一个管理界面和内容模型。
2. 内容集中存储：CMS存储数据库或存储库中的结构化内容。
3. 前端获取内容：网站、移动应用或其他客户端通过API或构建获取内容。
4. 演示是分开的：前端决定如何渲染内容。

| 模型           | 内容存储   | 发货               | 典型适配性         |
| :----------- | :----- | :--------------- | :------------ |
| 传统CMS        | 数据库    | 由CMS运行时渲染的       | 一个系统管理的简单站点   |
| API无头CMS     | 数据库    | REST/GraphQL API | 多频道内容、应用、复杂模型 |
| 基于 Git 的 CMS | Git 文件 | 构建输出/静态文件        | 静态站点，文档，编辑工作流 |

## B. 利益和取舍问题

当相同内容需要到达多个前端或前端团队想要完全控制渲染时，无头CMS平台是有用的。他们还可以引入操作复杂性：你管理一个内容服务、API计划、前端整合和部署管道。

共同的取舍包括：

- 灵活性与复杂程度：你获得了前端自由，但你建造了更多的交货堆栈。
- 结构化内容与写入流程：结构化模型很强，但是对于长形式的写入，它们可能感到僵硬。
- 销售商/API依赖关系：如果您的内容模型或 API 是专有的，托管平台可以创建迁移工作。

## 基于 Git 的 CMS 工具适合的地方

基于 Git 的 CMS 可以支持无头式的交货，当内容作为文件存储并被静态站点生成器或构建过程消耗时。关键区别是存储：内容位于Git存储库，而不是管理的数据库 API。

这种模型对于内容可转移性和Git历史很重要的博客、文件和营销站点很有效。对于具有复杂关系和实时传送的多频道应用程序来说，API-第一个无头的 CMS可能较为合适。
