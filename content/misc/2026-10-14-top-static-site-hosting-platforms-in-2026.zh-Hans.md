大多数静态站点主机可以在几分钟内部署一个Astro、Hugo、Jekyl、Eleventy或Zola站点。您第一次部署后出现了真正的差异：带宽限制，构建配额， 预览工作流、商业用途规则以及当你的网站需要服务器端功能时会发生什么事情。

## 静态主机比较

| 主机           | 适合度好                           | 主要交易                 |
| :----------- | :----------------------------- | :------------------- |
| GitHub Pages | 已经在 GitHub 上的公共项目网站            | 有限的平台功能和使用限制         |
| 云端页面         | 具有可变流量的静态站点                    | 叠加层和功能与云层工人拆分        |
| Vercel       | 前端应用程序需要预览和框架集成                | 计划限额和商业用途规则需要注意。     |
| 网络化          | Jambstack 站点需要表单、功能和预览         | 信用和使用价格可能更难预测        |
| Surge.sh     | CLI 第一静态部署和快速演示模式              | 团队工作流和 CI/CD 仪表盘功能减少 |
| 废旧边缘         | 需要WebAssembly或自定义运行时间的测试       | 较小的静态站点生态系统          |
| Deno Deploy  | 现有的 JavaScript/TypeScript 边缘部署 | 平台状态和迁移指南应优先检查       |

上面的每个选项都可靠地为纯HTML和CSS服务。 所以您的选择通常取决于账单的可预测性和您计划稍后添加多少服务器端行为。

## GitHub Pages

GitHub 页面是你的资源库已经在 GitHub 上生活的最简单的选择，你想要公共站点提供文档。 项目页面或个人博客。请先检查GitHub当前的使用限制和允许使用政策，然后再放入商业网站。

## 云端页面

云层页面对需要全局CDN传送和基于Git的部署的静态站点运作良好，而不必担心静态资产带宽的飞跃。如果您希望稍后添加服务器端功能，请在锁定您的设置前先检查 Cloudflare当前对页面、 功能和员工的指导。

## Vercel

Vercel的前端团队依靠拉请求预览部署和严格的框架整合。它往往是下一步的最顺利路径，尽管它也很好地设置了普通静态站点。请确保您的预期流量和商业使用量符合您选择的计划层级。

## 网络化

当你想要托管捆绑在一个地方的部署预览、表格、无服务器功能或身份时，Netlify是有意义的。折衷是成本的可预测性：审查其信用和使用模式如何适用于您的流量，并在承付之前生成时间。

## Surge.sh

Surge.sh是一个由 CLI 驱动的静态主机，为您的终端中的快速、直接上传而成。当您不需要完整的 CI/CD 仪表板或团队审核用户界面时，快速演示和普通静态站点非常有效。

## 废旧边缘

Wasmer 边缘专注于WebAssembly和多运行时部署。对于标准静态博客，它可能比您需要的更多平台。 但你的项目是否依靠它的运行模式是值得评估的。

## Deno Deploy

Deno 部署工具已用于边缘的 JavaScript 和 TypeScript 工作负荷。在开始一个新的长期项目之前，验证Deno当前平台状态和迁移指南。

### 匹配您站点的主机

- 简单的公共文档或个人博客：GitHub 页面、云层页面或Surge.sh。
- 带有预览重型拉取请求和无服务器功能的前端应用程序：Vercel或Netlife。
- 一个静态站点，稍后可能会发展成边缘计算：云Flare页面和工人。

在移动现场之前，检查供应商目前的定价页面、计划限制、商业用途政策、建立配额和框架支持。一旦您的网站获得真正的流量，一个免费的小演示主机可能会变得昂贵或具有限制性。
