## Section 1: Executive Summary

### 1.1 Scope and Audience

This document supports engineering leaders, platform owners, and procurement reviewers who must select a hosting platform for a web project in 2026. It evaluates three widely adopted providers — **Cloudflare Pages**, **Vercel**, and **Netlify** — against the workloads most teams actually ship: static marketing sites, documentation portals, server-rendered applications, and Jamstack projects that combine static frontends with API surfaces. The analysis is intentionally scoped to platform selection; it does not cover build tooling, CI/CD orchestration, or content management systems, except where a platform's bundled features materially affect the decision.

The guidance is provider-neutral and evidence-driven. All factual claims regarding pricing models, runtime behavior, and free-tier allowances are drawn from current provider documentation as supplied for this review. Because free tiers, bandwidth caps, and overage rules change frequently, every quantitative figure should be re-verified against each provider's official pricing page before a production commitment is signed. Where exact numbers would be required for a binding decision, this document flags the gap explicitly rather than stating a value that may be outdated by the time it is read.

### 1.2 Recommendation at a Glance

There is no universal winner among the three platforms. The correct choice depends on what is being built, how the team prefers to deploy, and how cost scales with traffic. The table below summarizes the headline recommendation; subsequent sections provide the supporting analysis.

Two cross cutting caveats apply to every recommendation. First, **runtime fit** matters as much as feature fit: dynamic workloads on Cloudflare Pages run on the Workers runtime, which differs from a conventional Node.js server and may require code changes. Second, **cost trajectory** matters as much as the headline price: Vercel's hobby tier is not licensed for commercial use, and paid-plan usage charges can rise quickly under high traffic, while Netlify's credit-based model ties cost directly to deploys, bandwidth, requests, and compute. Teams should treat the free tier as a proof-of-concept surface and model production cost separately before committing.

The remainder of this document defines the evaluation framework, profiles each platform in turn, compares their pricing behavior, and closes with a decision framework and pre commitment checklist. **Section 2** establishes the workload categories and criteria that structure the per-platform analysis.

## Section 2: Platform Overview and Selection Criteria

### 2.1 Workload Categories Considered

Platform selection begins with an honest classification of the workload, because each of the three providers optimizes for a different point on the spectrum from fully static delivery to fully dynamic computation. This document evaluates candidates against four workload categories that cover the majority of web projects undertaken by product and engineering teams.

**Static sites** are the simplest category: pre-built HTML, CSS, JavaScript, and assets served as-is from a CDN, with no server-side execution at request time. Typical examples include company blogs, documentation portals, product landing pages, and marketing microsites. For this category, the decisive factors are global delivery speed, bandwidth allowances, and request pricing — the dimensions on which Cloudflare Pages is strongest, with its free offering including unlimited static asset requests.

**Server-rendered applications** execute code on every request to produce personalized or data-driven HTML. Frameworks such as Next.js make this pattern mainstream, and it demands a runtime that can run application logic close to the user. Vercel is purpose-built for this workload, integrating server rendering, image optimization, and preview deployments into a single polished workflow. The evaluation therefore weighs runtime fidelity and framework integration heavily here.

**Jamstack projects** occupy the middle ground: a static frontend deployed from Git, augmented with API-driven functionality through serverless functions, forms handling, or identity services supplied by the platform itself. Netlify has historically defined this category, and teams that want those platform features bundled — rather than assembled from separate services — will weight this category accordingly.

**Frontend apps with separately hosted APIs** form the fourth category: a rich single-page application whose backend lives elsewhere (a conventional server, an internal API gateway, or a dedicated API product). In this case the hosting platform's job is purely static delivery, and criteria collapse toward performance, bandwidth economics, and deploy workflow simplicity — which is why this workload favors Cloudflare Pages, with its access to adjacent Cloudflare services such as Workers, R2, and D1 when light backend logic is later needed.

Teams should classify their project into one of these categories before comparing providers, because the categories map directly onto the recommendations in Section 7.

### 2.2 Evaluation Criteria

Five criteria structure the per-platform analysis in Sections 3 through 5. They are ordered by the weight most teams apply in practice, and each is defined precisely so that the same measure is used consistently across all three platform profiles.

1. **Delivery performance.** How quickly and reliably the platform serves assets to a globally distributed audience, including the footprint of the edge network and caching behavior. Evidence for this criterion comes from provider architecture documentation rather than from synthetic benchmarks, which vary too widely by region to be quoted here.
2. **Developer experience and deploy workflow.** The friction of going from Git push to production, including preview deployments for review, rollback behavior, and the polish of the surrounding tooling. Vercel and Netlify both compete strongly here; Cloudflare Pages offers a capable but comparatively lean workflow.
3. **Ecosystem and framework fit.** How well the platform supports the frameworks and adjacent services a team already uses — first-party framework integrations, image optimization, and access to storage, database, or compute services without leaving the provider. Runtime compatibility is assessed under this criterion: notably, dynamic applications on Cloudflare Pages require Cloudflare Workers, whose runtime differs from a conventional Node.js server.
4. **Cost trajectory.** Not the headline free-tier price, but how cost behaves as traffic and usage grow. This document deliberately treats pricing as a comparative exercise in Section 6, because the three providers use structurally different models: Cloudflare includes unlimited static asset requests on its free offering; Vercel uses plan-based allowances plus usage charges; Netlify uses a credit-based model spanning deploys, bandwidth, requests, and compute.
5. **Commercial and licensing constraints.** Terms that restrict how a plan may be used — most significantly, that Vercel's hobby tier is not licensed for commercial use, which immediately disqualifies it for revenue-generating projects on that plan.

One dependency should be flagged: Sections 3–5 apply these criteria qualitatively, while Section 6 adds the quantitative pricing comparison. Readers who need only a decision should proceed to Section 7, where the criteria are compressed into explicit decision rules and a pre-commitment checklist.

## Section 3: Cloudflare Pages

### 3.1 Strengths and Best-Fit Workloads

Cloudflare Pages is the strongest fit for blogs, documentation portals, landing pages, and frontend applications whose APIs are hosted separately. The platform's defining advantage is delivery performance: static assets are served from Cloudflare's global edge network, which places content geographically close to users and makes the platform particularly compelling for sites with an international readership. For the static-site and frontend-app workload categories defined in Section 2.1, this edge-first architecture directly serves the first evaluation criterion, and few competitors match its combination of speed and bandwidth generosity at the low end of the price spectrum.

The economic profile reinforces this positioning. Cloudflare Pages includes **unlimited static asset requests on its free offering**, which means teams can operate documentation portals or content-heavy blogs without anticipating a request-count ceiling as traffic grows. This is a structurally different proposition from the allowance-plus-overage models used by Vercel and Netlify, and it is developed fully in the pricing comparison in Section 6. For organizations that want predictable behavior as a site gains traffic, this allowance structure removes one of the most common sources of surprise bills.

A second differentiator is ecosystem adjacency. Cloudflare Pages does not operate in isolation; it sits inside a broader platform that includes **Workers** (edge compute), **R2** (object storage), and **D1** (serverless SQL database). Teams that later need light backend logic — a contact-form handler, a configuration API, image transformations — can attach a Worker without procuring a second provider or re-architecting the frontend. This makes the platform a pragmatic choice for the "frontend apps with separately hosted APIs" category: the API can remain on conventional infrastructure while the Pages frontend enjoys edge delivery, with Workers available as an optional escape hatch for incremental dynamic needs.

The developer experience is competent and Git-based, supporting the standard push-to-deploy flow. It is comparatively leaner than Vercel's or Netlify's offerings in preview tooling and framework-specific integrations, but for teams whose primary requirement is reliable static delivery, the leaner surface area is a manageable trade rather than a deficiency.

### 3.2 Trade-offs and Constraints

The principal trade-off concerns dynamic workloads. Applications that require server-side execution on Cloudflare generally run on **Cloudflare Workers**, and the Workers runtime differs from a conventional Node.js server. In practice this means code that depends on Node.js-specific APIs, middleware conventions, or long-running server processes may need adaptation — and in some cases rework — before it executes correctly at the edge. Teams evaluating Cloudflare Pages for a server-rendered application should therefore treat runtime compatibility as a gating question, not an afterthought: verify that the chosen framework and its dependencies run on Workers before committing to a migration.

A second, softer constraint follows from the same architecture. Because the platform's center of gravity is static delivery plus edge compute, teams that rely on deeply integrated framework features — server rendering with sophisticated caching semantics, image optimization pipelines, or extensive preview workflows — may find that Cloudflare Pages offers fewer of these conveniences out of the box than Vercel does for Next.js or Netlify does for Jamstack projects. This does not make the platform unsuitable for such projects, but it shifts integration effort onto the team.

Finally, a scope boundary should be stated explicitly: Cloudflare Pages is not the recommendation for teams seeking the most polished server-rendered application workflow. That workload belongs to Vercel, profiled next. The decision rule is straightforward — when the project is primarily static with optional light dynamic functions, Cloudflare Pages delivers exceptional economics and performance; when the project is server-rendered from day one, the runtime difference becomes the deciding factor against it.

## Section 4: Vercel

### 4.1 Strengths and Best-Fit Workloads

Vercel is the strongest fit for server-rendered applications and for teams that place a premium on a polished preview-and-deploy workflow. Where Cloudflare Pages, profiled in Section 3, is optimized around static edge delivery, Vercel is optimized around the full lifecycle of a dynamic application: build, preview, render, and serve. For the server-rendered workload category defined in Section 2.1, it is the natural first candidate, and the analysis below explains why that positioning holds.

The platform's core strength is framework integration. Vercel integrates well with modern frameworks and deployment workflows, including server rendering, image optimization, and preview deployments, and this integration is deepest for Next.js — a framework developed by the same company. Teams building Next.js applications benefit from first-party support for server rendering and image optimization, features that would otherwise require deliberate engineering effort to replicate on generic hosting. The practical consequence is a shorter path from repository to production and fewer infrastructure decisions delegated to the application team.

The second strength is the developer experience surrounding deployment. Vercel's preview-and-deploy workflow is widely regarded as the benchmark in this market: every pull request receives a deployable preview, which shortens review cycles and lets product stakeholders evaluate changes before merge. For teams that ship frequently and rely on asynchronous review, this workflow quality is not a cosmetic benefit; it measurably reduces coordination overhead between engineering, design, and product functions. The developer-experience criterion defined in Section 2.2 weights this directly, and Vercel scores at or near the top of the three platforms.

Operationally, Vercel also removes much of the server-management burden that a conventional Node.js deployment carries. Teams do not provision or maintain render servers; the platform handles scaling and routing for server-rendered output. For engineering organizations without a dedicated infrastructure function, this significantly lowers the operational floor compared with self-hosting.

### 4.2 Trade-offs and Constraints

The principal constraint is licensing on the free tier. **The hobby tier is not licensed for commercial use**, which immediately disqualifies it for revenue-generating projects, client work, or any production deployment operated by a business. Teams must therefore evaluate Vercel on the assumption that production usage requires a paid plan — a structural difference from Cloudflare Pages, whose free offering carries unlimited static asset requests and no equivalent commercial-use restriction on that surface.

The second constraint is cost trajectory. Paid-plan bandwidth and usage costs **can rise quickly for high-traffic projects**, because Vercel's model combines plan-based allowances with usage charges beyond them. The direction of this risk is predictable — cost grows with traffic — but the magnitude depends on workload characteristics such as image-heavy pages, cache hit rates, and the proportion of server-rendered requests. Section 6 develops this comparison in detail, and the pre-commitment checklist in Section 7.2 makes price verification a mandatory step: teams should review current plan details and model production usage before selecting Vercel for a high-traffic deployment.

A third, narrower trade-off concerns ecosystem lock-in direction. Vercel's advantages concentrate around its supported frameworks and its proprietary workflow; a project that outgrows the platform or migrates away for cost reasons may need to rework deployment configuration and, in some server-rendering cases, adapt runtime assumptions. This is not a reason to avoid Vercel — for Next.js-first teams the trade remains favorable — but it is a reason to document the deployment boundary early, so that the exit path is understood before deep integration accumulates.

Finally, a scope boundary: Vercel is not the recommendation for teams whose project is a simple static site with no server-rendered components. For that workload, Cloudflare Pages delivers comparable performance with materially better free-tier economics, and Netlify offers a comparable feature set with a different cost model. The next section profiles that middle path.

## Section 5: Netlify

### 5.1 Strengths and Best-Fit Workloads

Netlify is the strongest fit for static sites, Astro projects, Jamstack sites, and teams that want Git-based deploys with built-in platform workflows. The platform's historical role is worth stating plainly: Netlify popularized the Jamstack model itself, and its feature set reflects that origin. Where Cloudflare Pages (Section 3) competes primarily on delivery economics and Vercel (Section 4) competes on the server-rendered application lifecycle, Netlify competes on the breadth of what is bundled — a single platform that handles deploys, previews, and the dynamic functions a Jamstack site needs without assembling additional services.

The first strength is mature Git-based deployment. Netlify provides well-established Git integrations that build and publish a site on every push, and this maturity matters: the deploy pipeline, rollback behavior, and build handling have been exercised by a large user base over many years, which reduces the operational risk of unusual repository configurations or complex build steps. For teams whose process is Git-centric by default, the platform requires almost no workflow change.

The second strength is deploy previews paired with serverless functions. As with Vercel, every proposed change receives a preview deployment for review; unlike purely static hosts, Netlify also supplies serverless functions natively, so form handling, authenticated routes, and API proxies can live inside the same project and repository as the frontend. The practical effect is architectural consolidation — **platform features reduce the need for extra services**. A Jamstack team that might otherwise combine a static host, a functions provider, and a forms service can meet those needs within one platform, one bill, and one deploy pipeline. For the Jamstack workload category defined in Section 2.1, this consolidation is the platform's central argument.

A third strength is first-class Astro support. Astro has become a leading framework for content-driven static sites, and teams building with it will find Netlify's tooling aligned with the framework's conventions. Combined with the mature deploy workflow, this makes the platform a low-friction default for content sites that may later grow interactive islands or API-backed features.

### 5.2 Trade-offs and Constraints

The principal trade-off is that Netlify is a breadth-first platform competing against depth-first specialists, and it **may have less of an edge than Cloudflare for simple static hosting or than Vercel for Next.js-first development**. Stated concretely: a team hosting a purely static documentation portal will generally find better free-tier economics on Cloudflare Pages, whose free offering includes unlimited static asset requests, while a team building a Next.js server-rendered product will generally find deeper first-party integration on Vercel. Netlify's positioning is therefore strongest in the middle of the workload spectrum — Jamstack projects with mixed static and dynamic needs — and weakest at either extreme, where a specialist platform holds a structural advantage.

The second constraint is the pricing model's complexity. Netlify **uses a credit-based model for deploys, bandwidth, requests, and compute**, which means cost depends on four consumption dimensions simultaneously rather than on a single meter. This structure is flexible in principle — teams pay roughly in proportion to what they actually use — but it makes cost harder to forecast than a flat plan or an unlimited-allowance model. Under traffic growth or frequent deploys, multiple meters move at once, and the combined effect can surprise teams that modeled only bandwidth. Section 6 compares this model directly against Cloudflare's and Vercel's, and the checklist in Section 7.2 requires teams to estimate usage across all four dimensions before committing.

Finally, a scope boundary consistent with the preceding sections: Netlify is not the recommendation when a project sits cleanly at one end of the spectrum. For pure static delivery, choose Cloudflare Pages; for Next.js-first server rendering, choose Vercel. For everything in between — and particularly for Astro- and Jamstack-based projects that want platform features bundled rather than assembled — Netlify remains the default candidate. Section 6 quantifies the pricing differences that separate these recommendations.

## Section 6: Comparative Pricing and Cost Trajectory

### 6.1 Free Tier and Allowances

The three providers price their services in structurally different ways, and understanding those structures matters more than comparing any single headline number. The table below summarizes the pricing model of each platform as established in the platform profiles in Sections 3 through 5.

| **Páginas do Cloudflare** | Generous static allowance             | **Unlimited static asset requests** included on the free offering  | Static asset requests (unlimited at free tier); dynamic compute via Workers priced separately |
| **Vermelha**              | Plan-based allowances + usage charges | Fixed plan allowances; hobby tier restricted to non-commercial use | Bandwidth; usage charges beyond plan allowances                                               |

_Note: This table characterizes pricing models, not specific dollar figures. All quantitative limits and prices must be verified on each provider's official pricing page before commitment, because free tiers and overage rules change frequently._

Two observations follow from the structural comparison. First, **Cloudflare Pages offers the most predictable free tier for static workloads**: unlimited static asset requests mean a documentation portal or blog can grow its readership without crossing an allowance threshold on that meter. The one caveat is scope — the unlimited allowance applies to static assets, and dynamic logic implemented through Workers is subject to separate Workers pricing, so a project that begins static and later adds substantial edge compute should model that compute growth explicitly. Second, **the free tiers of Vercel and Netlify are best understood as proof-of-concept surfaces rather than production surfaces**. Vercel's hobby tier additionally carries the licensing restriction discussed in Section 4 — it is not for commercial use — which makes the paid-plan question mandatory rather than optional for any business deployment.

### 6.2 Cost Behavior at Scale

At production traffic levels, the cost risk of each platform concentrates in a different dimension, and teams should model the dimension that matches their workload profile rather than all dimensions uniformly.

**Cloudflare Pages** presents the lowest cost risk for static-heavy projects. Because static asset requests are unlimited on the free offering, traffic growth in the static dimension does not translate into escalating bills on that meter. The cost curve only steepens if the project migrates dynamic logic onto Workers, where compute is metered; for the recommended workloads — blogs, documentation, landing pages, frontend apps with separately hosted APIs — this dimension typically remains modest. The residual risk is therefore architectural rather than financial: the cost stays low precisely as long as the workload stays static.

**Vercel** presents the highest cost-growth risk among the three for high-traffic projects, because paid-plan bandwidth and usage charges **can rise quickly** as traffic increases. Server-rendered pages meter on every request, image-heavy layouts consume bandwidth faster than text-heavy ones, and cache configuration materially changes the effective cost per visit. For a Next.js production deployment, the correct procedure is to model expected monthly requests and bandwidth against current plan allowances and to price the overage path explicitly — the checklist in Section 7.2 operationalizes this step. The licensing constraint compounds the financial one: a commercial project has no free tier to fall back on, so the paid plan is the floor, not the ceiling.

**Netlify** presents a forecast-complexity risk rather than a single-dimension growth risk. Because credits span **deploys, bandwidth, requests, and compute**, four meters move simultaneously as a project scales, and frequent deploys or function-heavy features can shift the cost mix even when traffic is stable. The model rewards teams that instrument their usage — reviewing consumption per dimension monthly — and penalizes those that budget on bandwidth alone. For Jamstack projects whose consumption profile is steady, the credit model is workable and competitive; for spiky or rapidly growing projects, the forecast burden is real and should be assigned an owner (see Section 7).

A single verification rule applies to all three providers and closes this section: **confirm current plan details, allowance limits, and overage rules on each provider's pricing page before signing**, since these terms change regularly and this document intentionally reports structures rather than volatile figures. ## Section 7: Recommendations and Decision Framework

### 7.1 Decision Rules by Workload

The analysis in Sections 3 through 6 reduces to a small set of decision rules that cover the common cases. Each rule maps a workload classification from Section 2.1 to a platform recommendation and names the deciding criterion, so that a reviewing engineer or engineering manager can trace the recommendation back to the evidence without re-reading the full document.

**Rule 1 — Static-first projects choose Cloudflare Pages.** If the project is a blog, documentation portal, landing page, or a frontend application whose APIs are hosted separately, select Cloudflare Pages. The deciding criteria are delivery performance and cost trajectory: global edge delivery is strong, and unlimited static asset requests on the free offering remove the request-count ceiling that constrains the other two platforms. Confirm that no significant server-side rendering is planned within the foreseeable roadmap, because dynamic workloads on Cloudflare require the Workers runtime, which differs from a conventional Node.js server (Section 3.2).

**Rule 2 — Server-rendered applications choose Vercel.** If the project renders HTML on the server per request — particularly a Next.js application — select Vercel. The deciding criteria are ecosystem fit and developer experience: first-party framework integration, server rendering, image optimization, and the preview-and-deploy workflow are the strongest among the three candidates. Two gates must be passed before commitment: the project must run on a paid plan, because the hobby tier is not licensed for commercial use, and projected traffic must be modeled against plan allowances, because usage charges can rise quickly for high-traffic projects (Sections 4.2 and 6.2).

**Rule 3 — Jamstack and Astro projects choose Netlify.** If the project combines a static frontend with platform-supplied dynamic features — serverless functions, forms handling, API proxies — and the team wants those features bundled, select Netlify. The deciding criteria are ecosystem fit and workflow consolidation: mature Git deployments, deploy previews, and serverless functions in one platform reduce the need for extra services. Accept the forecast burden that follows: the credit-based model meters deploys, bandwidth, requests, and compute simultaneously, so consumption must be reviewed per dimension, not on bandwidth alone (Sections 5.2 and 6.2).

**Rule 4 — When a project sits at an extreme, prefer the specialist.** As established in Section 5.2, Netlify may have less of an edge than Cloudflare for simple static hosting or than Vercel for Next.js-first development. Teams whose project sits cleanly at one end of the spectrum should apply Rule 1 or Rule 2 rather than defaulting to the all-rounder.

**Ownership note:** the workload classification and rule selection should be owned by the technical lead of the project; the cost verification in Rule 2 and Rule 3 should be co-owned with whoever holds the budget, so that the pricing check is not skipped under schedule pressure.

### 7.2 Pre-Commitment Checklist

Before any provider is selected for production, the following steps should be completed and recorded. Each item reflects a specific risk identified earlier in the document.

1. **Verify current pricing and limits.** Confirm the latest plan details, allowance limits, and overage rules on each provider's pricing page. Free tiers and overage rules change regularly, and this document intentionally reports structures rather than volatile figures (Section 6).
2. **Confirm the commercial-use gate for Vercel.** If any plan under consideration is the Vercel hobby tier, confirm the project is not commercial; otherwise move to a paid plan before any production deployment (Section 4.2).
3. **Test runtime compatibility on Cloudflare.** For projects with dynamic logic headed to Cloudflare, validate that the framework and its dependencies execute correctly on the Workers runtime before migration, not after (Section 3.2).
4. **Model production cost in all metered dimensions.** For Vercel, model bandwidth and usage against plan allowances; for Netlify, estimate deploys, bandwidth, requests, and compute as four separate line items (Section 6.2).
5. **Assign a cost owner.** Name the person responsible for monthly usage review after launch, so that cost trajectory is monitored rather than discovered (Section 6.2).
