Git based CMS tools let you edit content in a browser while keeping the actual content in a Git repository. 这给了您版本历史，拉取请求，以及您可以稍后移动的普通文件。困难的部分是选择一个，因为它们都许诺“易于编辑”，并且意味着非常不同。

Some are form-based, some edit on the page, some are built for developers, and some are trying to make writing comfortable for nontechnical people. 正确的选择取决于谁发布以及您的内容需要多少结构。

## 快速比较

| CMS         | 最好的                | 编辑样式      | 要检查的事项               |
| ----------- | ------------------ | --------- | -------------------- |
| 去除CMS       | 配置的收藏和已建立的 Git 工作流 | 基于表格的管理界面 | 当前维护，Git 提供商，认证设置    |
| TinaCMS     | 可视化/上下文编辑          | 页面上或结构化编辑 | 当前定价，自动托管，schema 工作流 |
| 静态键         | 开发者定义的方案           | 由代码生成的表单  | 当前框架支持，云/本地模式        |
| 页面CMS       | 简单的 GitHub 编辑      | 基于表格的仪表板  | 当前Git提供商支持，许可协议      |
| Sveltia CMS | 轻量化浏览器编辑           | Git上的管理界面 | 目前的特征均等和成熟度          |
| 云塔          | 机构/客户管理网站          | 视觉/编辑工作流  | 当前定价和托管模式            |
| LightCMS    | 作者发布静态站点内容         | 文档编辑器     | 当前功能、主机、 Git提供商支持    |

## 如何选择

从编辑器开始，而不是特征列表。 If writers are publishing long-form articles, a document editor usually feels better than a form with a Markdown text area. 如果您的内容是结构化记录、表格和方案更合适。

接下来，请检查版本库工作流程。确认图像在哪里，如何处理前缀，支持哪些Git提供商，以及工具是否适合您的静态站点生成器。在演示中看起来很好的CMS仍然会令人烦恼，如果它写到前面的事物，您的模板不会预料到。

最后，坦诚地对待行动。一个自我托管的工具可以让您控制，但是您自己的设置和更新。托管工具可以减少维护，但您需要放松定价和对供应商的依赖。

## LightCMS适合的位置

LightCMS is for people who want to write in a browser and still keep the Git based workflow. 当主要任务是将文章、文件或营销内容发布到静态站点时，这种做法很适合。 It’s not the right fit when you need a database based content API, complex relational content models, or heavy enterprise governance.

如果您正在比较选项，不要停止功能矩阵。在每个工具上尝试相同的真正任务：撰写一个帖子，添加一个图像，编辑前沿事项，发布并确认站点构建。这很快告诉你哪个适合你的团队。 See [Git based CMS vs Traditional CMS](/blog/git-cms-vs-traditional-cms/) and [Getting Started with LightCMS](/getting-started/).
