LightCMS 和 Pages CMS 都在 Git 中将您的内容存储为文件，因此您永远不会失去对您的资源库的所有权。真正的分割是您花费大部分时间编辑的内容：长形式的Markdown 文章或结构化前事项字段。

页面CMS将表单字段和收藏模式放在第一位，而LightCMS则将视觉文档编辑器放在第一位。

## 编辑模型的比较


| 区域            | LightCMS                        | 页面CMS             |
|:------------- |:------------------------------- |:----------------- |
| 主接口           | Tip点击视觉标记编辑器                    | 配置驱动的表单编辑器        |
| 最合适的          | 长式文章、文件和文章                      | 结构化记录、目录和元数据繁多的条目 |
| 内容存储          | 在 GitHub 中带有前缀的Markdown         | GitHub 文件和媒体      |
| 配置            | GitHub 应用程序连接 (PostgreSQL 需要自机) | 定义收藏和字段的仓库配置文件    |
| 正在写入 Workflow | 草稿，格式化，图像粘贴，AI 起草，语音听音          | 字段验证、选择、日期和富文本输入  |


这种差异显示了您打开帖子的时刻：LightCMS感觉像一个写作桌面， 而Pages CMS 感觉就像您的资源库中的管理表单一样。

## 当页面CMS是更好的选择

当你的网站围绕结构化记录而不是长形式的探索构建时，页面CMS就更有意义。如果您保持目录、更新日志、产品列表或自定义日期的页面、选择、布尔值， 嵌套的前事项字段最为重要，定义配置文件中的方案使得编辑器不会中断您的构建。

如果您不想运行一个 CMS 本身的应用程序数据库，那么采纳也会更轻松。

## 当LightCMS是更好的选择

当主要任务是撰写和编辑文章时，LightCMS会更适合。如果您或您的作者在当天大部分时间内草拟了标题、代码块、表格等1,000字帖子， 和内联图像，基于浏览器的文档编辑器比一堆表单输入更快。

在选择任一工具之前，根据您的资源库的实际布局、前事项格式和图像文件夹协议进行测试。 For nearby Git based options, see [LightCMS vs. Decap CMS](/comparison/lightcms-vs-decap-cms/) and [LightCMS vs. Keystatic](/comparison/lightcms-vs-keystatic/).
